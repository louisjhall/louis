### Media completeness — current implementation

- **Not stored as an authoritative single field.** Instead computed on demand:
  - `run_exercise_media_scan()` (`feature_exercise_content.py:843`) walks `exercises_v2`, checks required-slot coverage from `demo_slots` / legacy `primary_image_id` / `demo_start_image_id` / `demo_end_image_id`, plus `content_status.video` and `content_status.coaching_points`. Missing anything → creates a `coach_task` of type `exercise_needs_*`.
  - `feature_flight_support_media._resolve_frames_and_maybe_queue()` builds the persona-fallback frame array and upserts a `media_queue` row when the preferred persona's slots are missing.
- **Two parallel queue mechanisms** (`coach_tasks` for training / `media_queue` for Flight Support) — they don't share a table, don't share fields, and don't share priority logic.

### Answer to §1 invariant

> Every movement visible in a client experience must resolve to ONE canonical movement/exercise identity.

**Status today: NO.** Reasons (proven with data, expanded in sections 2–8):

1. **V2 workouts arrive at the client via `_spec_to_exercises()` (`feature_v2_client_bridge.py:133`) which reads free-text `name` from `payload.exercises[]` and returns `{ name, exercise_name_display, sets, reps, … }` with NO `exercise_id`.** The client renderer therefore never has a canonical id to look up.
2. **Warm-ups / cool-downs / drills inside V2 session specs use free-text names too** (Pietro's sample: `"Ankle circles"`, `"Leg swings (front/back)"`, `"Leg swings (side)"` — all live in `payload.warmup.drills[]`, none carry an id).
3. **Aviation Support (Flight Support) protocols in `feature_aviation_support.py` list blocks as `{ name: "Thoracic rotation", duration_sec: 60, cue: … }` — 19 unique names sampled; only 5/19 have a corresponding `exercises_v2` record** by regex-name-match.
4. **The `exercises_v2.alternatives` array (populated for 120 of 364 rows) is a list of free-text strings, not a list of `exercise_id`s.** Nothing enforces that each alternative name resolves to a Library record.
5. **Substitution engine** (`feature_workout_guardrails._SUBSTITUTIONS`) maps a movement pattern to a free-text `name` — no id.
6. **Change-Setup engine** (`feature_v2_p7_equipment._adapt`) **does** carry `exercise_id` through — it's the one place in the audit where the canonical link survives (line 224).

## 2. Duplicate protection — DB RDL vs Dumbbell RDL

- **No aliases table** on `exercises_v2`. The unique key is a raw `id (UUID)` — the `exercise_name` field is not indexed as unique or fuzzy-matched.
- **No canonical_name normaliser** at creation time (`ex_create` in `feature_exercise_content.py:454` accepts any string).
- The frontend Library page has a client-side search across `exercise_name` / `category` — no server-side dedupe.
- **Risk: MEDIUM.** A coach who types "DB RDL" and another who types "Dumbbell RDL" creates two rows and two independent media requirements. Nothing currently prevents this.

## 3. Variant vs duplicate

The schema has `movement_pattern`, `equipment_type[]`, and `difficulty_level`, so the correct information is present to distinguish:
- `Romanian Deadlift` vs `Single-Leg Romanian Deadlift` via `movement_pattern` = "hinge" + name/tags variant.
- `Cable Row` vs `Resistance Band Row` via `equipment_type` = ["cable"] vs ["band"].

However **nothing today groups records into a "movement family" cluster** — no `movement_family_id` field. A future canonical-family index would ride on top of `movement_pattern` + `body_area` + `equipment_type`.

## 4. Library page filters + usage indicators (current UI)

- Sort/filter surface: category, subcategory, training_type, body_area, difficulty_level, status, `approval_status`, `used_in_upcoming_workouts_count`.
- Media indicators visible: `primary_image_id`, `demo_start_image_id`, `demo_end_image_id`, `content_status`, `approved_image_status`, `approved_video_status`.
- What's **missing** from the current UI (for the Media-Ops-Hub future):
  - No "Live primary vs available alternative" split.
  - No filter "Flight Support" — Flight Support blocks aren't tracked as Library rows at all.
  - No "Needs Media" filter that unifies coach_tasks + media_queue.
  - No "Client-visible" filter (because we don't yet know which alternatives are client-visible; see §5 of the Alternatives audit).

## 5. Automatic completion — feasibility

- `run_exercise_media_scan()` already checks required-slot coverage and skips exercises that pass (`if not missing: continue`).
- On the Flight Support side `_upsert_media_queue` writes `status: "needs_media" | "complete"` based on the same slot coverage.
- **Feasible.** Once an image is added → `demo_slots` map updated → the very next scan flips status to complete without any manual task closure. This behaviour is already deterministic; the only piece missing is a **single unified `media_queue`** that both training and Flight Support share.

## 9. GF / Fat Loss variety pools

- `feature_v2_variety.py` selects from slot templates in `workout_slot_templates` where the slot definitions carry `exercise_id`. The variety pool per slot is bounded (typically 2–5 rows), all pulled from `exercises_v2`.

## 12. Implementation complexity

**Estimate: MEDIUM–LARGE.**

- **Small** (a day of surgical work each): unifying `media_queue`, adding a `movement_family_id` field, extending the Library page with Needs-Media / Live-primary / Alternative filters, and killing the legacy V1 fallback alternatives dict.
- **Medium**: rewriting `feature_workout_fallback` and `feature_workout_guardrails` to emit `exercise_id` (and killing V1 free-text alternatives).
- **Large**: migrating **19+ Aviation-Support block names to canonical `exercises_v2` records** with pilot-persona image sequences, plus adding a Flight-Support-alternative concept where currently none exists.
- **Largest single risk**: V2 construction (`_spec_to_exercises` / `feature_v2_construction_v2`) currently emits **free-text `name`** for every primary exercise. Making that carry `exercise_id` end-to-end is the biggest change — it touches the planner, the client bridge, and the client renderer. Everything else assumes this piece exists.
